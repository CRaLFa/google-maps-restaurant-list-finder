# Google マップの「公式レストランリスト」を地図から探せるようにした話

- 実機の自動操作で集めて、12 日で Cloud Run に公開するまで
- 2026-07-26 〜 2026-08-06 / 92 コミット / 8 PR

---

# レストランリストとは

- Google マップがエリアごとに自動生成している公式のおすすめ店一覧 (2024 年 4 月発表)
- 🏆 トップリスト: 定番の人気店 / 💎 地元で人気: 隠れた名店 / 📢 トレンド: 急上昇 (毎週更新)
- アプリでエリア名を検索し、下のシートをスワイプすると出てくる
- つまり「エリア名か掲載店を先に知っていないと辿り着けない」

---

# 困っていたこと

- Google Takeout では自分が作ったリストしか取れず、フォローした公式リストの中身は出てこない
- 「渋谷: トップリスト」のようなリストが全国にどれだけあるのか一覧する手段が無い
- 461 件フォローしていたが、アプリや Web の「保存済み」は表示数に上限があり全件を確認できない

---

# 作ったもの

- 地図のピンをクリックするとそのエリアのリスト (最大 3 種類) へ飛べる
- 地名のインクリメンタル検索でピンとツリーを絞る (「名古屋」で市内の区が出る)
- 都道府県 ▶ 市 ▶ 区 ▶ エリア ▶ リストのツリー、全国地方公共団体コード順
- 漏れているエリアを報告できるフォーム
- 現在 200 エリア / 597 リスト。ダークモードとスマホ表示に対応

---

# 全体構成

- 収集: Python + adb + uiautomator で実機の Google マップアプリを自動操作
- 座標: 共有 URL を PC の実ブラウザで開いて取得 (agent-browser)
- データ: Firestore (Native、名前付きデータベース)
- サーバ: Go / Cloud Run 1 サービス。静的ファイルは go:embed でバイナリ 1 個
- フロント: 単一 HTML + Maps JavaScript API + Pico.css。ビルド無し
- スパム対策: reCAPTCHA Enterprise + サーバ側レート制限

---

# 収集編 1: 実機を adb で操作する

- リスト一覧は API で取れず、Web 版の Google マップにも出てこない。残る経路は実機のアプリだけ
- 「保存済み」画面を uiautomator dump で読み、リスト名を全件収集
- 各リストの「共有」→「クリップボードにコピー」を叩き、adb-clip でクリップボードを読む
- 番兵をクリップボードに置いてから叩き、更新されなければリトライ
- 1 件 20〜25 秒、461 件で 2.5〜3 時間。中断しても Firestore に upsert 済みの分は飛ばして再開できる
- am start を連打すると Maps が ANR。画面再構築は最後の手段にした

---

# 収集編 2: 座標は curl では取れない

- 集まった共有 URL に座標は入っていない。ピンを地図に置くには緯度経度が要る
- 共有 URL は座標無しの URL にリダイレクトし、SPA が読み終わってから replaceState で @lat,lng,zoom が付く
- 実ブラウザで JS を動かして URL を待つしかない
- 同一タブで続けて開くと再センタリングされないので毎回 about:blank を挟む
- 座標は既定センター (東京駅付近) → 実際の中心の 2 段階で変わる。安定するまでポーリング

---

# 一番ハマった話: ピンが全部西にずれていた

- OSM の行政境界と突き合わせると 155 エリア中 153 件が西寄り。中央値 3.5 km、最大 30 km (大津市)
- 原因は Google マップの左パネル (480px)。URL の中心は地図キャンバス全体の中心なので、常に 240px 分だけ西を指す
- 補正式: lng += panel/2 × 360 / (256 × 2^zoom)
- 補正後は境界外が 34 → 0 件、経度差の中央値は 3.5 km → 27 m
- 緯度は完全一致で経度だけ動くことが「場所ではなくブラウザの都合」の裏付けになった

---

# 設計判断: 何を選び、何を捨てたか

- Leaflet + OSM → 却下。扱っているのが Google マップのリストなので地図も揃える
- Cloud SQL → 却下。600 件弱に常時課金は重い
- Firebase Hosting から Firestore 直書き → 却下。サーバ側の検証とレート制限を効かせたい
- 静的 TSV のまま → 却下。報告の書き込みができない
- 選んだのは Firestore + Cloud Run 1 サービス。TSV は初回インポートと復旧用にだけ残す

---

# フロントの割り切り

- ビルド無しの単一 HTML。ツリーは details/summary、報告フォームは dialog。オーバーレイ・フォーカス管理・Esc 閉じはブラウザ任せ
- CSS は Water / Simple / Pico を比較し、dialog と details が仕上がっている Pico.css を採用
- ツリーの階層はデータモデルを変えず、所在地 + エリア名のフルパスから機械的に導く
- 都道府県・市区町村の並びは総務省の自治体コード表 (1,965 行) を 1 ファイルに寄せ、Go とフロントの両方から使う
- 191 個のピンが東京で重なるがクラスタリングは入れない。ズームで足りる

# 運用

- Cloud Build のトリガ 2 本。PR は検査のみ、master への push で検査 + デプロイ
- 検査は Go (vet/test)、Python の自己チェック、Node のツリー検証。Firestore に触らないので CI に権限は不要
- ドキュメントだけの変更はトリガの ignored-files でビルドを起こさない
- Firestore はスケジュールバックアップ。報告はコンソールで見てトリアージ

---

# 学び

- curl で見えないものは実ブラウザに任せる。SPA の URL 書き換えは待つしかない
- 「ずれている気がする」はデータで検証する。OSM 境界との突合で原因と補正の妥当性が両方言えた
- Firestore の (default) データベースはリネームできない。最初から名前を付ける
- 静的な地名データの持ち場は 1 つにする。Go とフロントで二重に持つと片方が古くなる
- Maps の API キーは公開 URL が確定してから作る。先に作ると制限の無い期間ができる
