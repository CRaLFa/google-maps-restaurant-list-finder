# Google マップの「公式レストランリスト」を地図から探せるようにした話

Google マップには、エリアごとに自動生成される公式のレストランリストがあります。
「渋谷: トップリスト」「金沢: 地元で人気」のような、Google が持っている興味と保存のデータから作られる一覧のことです。
便利なのですが、エリア名を先に知っていないと辿り着けません。
全国にどれだけあるのかを一覧する手段もありません。

そこで、地図のピンから辿れる Web アプリを作りました。

<https://google-maps-restaurant-list-finder-bxnbzgrdda-an.a.run.app>

現在 200 エリア / 597 リストを収録しています。
開発期間は 12 日、92 コミット、8 PR。
リストの収集に実機の Google マップアプリを自動操作したところ、集めた座標が全件西にずれるという現象に当たりました。
この記事では、作ったものの構成と、そのずれの原因を突き止めるまでを書きます。

## レストランリストとは何か

**レストランリスト**は、Google マップがエリアごとに用意している公式のおすすめレストラン一覧です。
[Google 公式ブログ](https://blog.google/intl/ja-jp/products/explore-get-answers/google-3/) で 2024 年 4 月に発表された機能で、ユーザーが作ったリストではなく、そのエリアで人々が興味を持っている店や保存している店のデータから自動で作られます。

エリアごとに 3 種類あります。

- **トップリスト**：常に人気の定番店。長年の実績がある店が並ぶ
- **地元で人気**：まだあまり知られていない近所の名店
- **トレンド**：最近人気が急上昇した店。毎週更新される

アプリでエリア名を検索し、下から出てくるシートを上にスワイプすると表示されます。
リストに載っている店の詳細を開けば、その店が入っているリストへのリンクからも辿れます。
いずれの経路でも、エリア名か掲載店のどちらかを先に知っている必要があります。

## 困っていたこと

筆者はこのリストを 460 件ほどフォローしていました。
そうなると、アプリの「保存済み」画面は一覧性が足りません。
フォローした覚えのあるリストを探すのに、延々とスクロールすることになります。

外に持ち出す手段もありませんでした。
Google Takeout で取れるのは自分が作ったリストだけで、フォローした公式リストの中身は出てきません。
「全国にどんなエリアのリストがあるのか」を知る方法が、どこにも用意されていないのです。

一覧が手に入らないなら、自分で集めるしかありません。

## 作ったもの

- 地図のピンをクリックすると、そのエリアの 3 種類のリストへのリンクが開く
- 地名のインクリメンタル検索でピンとツリーを同時に絞る (「名古屋」と打てば市内の区が出る)
- 都道府県から市、区、エリア、リストへと降りるツリー。並び順は全国地方公共団体コード順
- 漏れているエリアを報告できるフォーム
- ダークモードとスマートフォン表示に対応

## 全体構成

| 層 | 選んだもの |
| --- | --- |
| 収集 | Python + adb + uiautomator で実機の Google マップアプリを操作 |
| 座標取得 | 共有 URL を PC の実ブラウザで開いて読む |
| データ | Firestore (Native モード、名前付きデータベース) |
| サーバ | Go / Cloud Run 1 サービス。静的ファイルは `go:embed` でバイナリ 1 個に同梱 |
| フロント | 単一 HTML + Maps JavaScript API + Pico.css。ビルド無し |
| スパム対策 | reCAPTCHA Enterprise + サーバ側レート制限 |

以下、収集側から順に見ていきます。

## 収集編 1: 実機を adb で操作する

リストの一覧は API で取れません。
Web 版の Google マップにも「保存済み」の公式リストは出てきません。
残る経路は、Android 実機のアプリを機械的に操作することでした。

手順はこうなります。

1. 「保存済み」画面を `uiautomator dump` で読み、リスト名を全件収集する
2. 各リストを開いて「共有」から「クリップボードにコピー」を叩く
3. 端末のクリップボードを読み、共有 URL を得る
4. Firestore に upsert する

クリップボードの読み取りには `adb-clip` (端末側で動かす小さなヘルパー) を使いました。
`adb shell` からクリップボードを直接読む手段が無いためです。

ここで問題になるのが、コピーが完了したかどうかを知る手段が無いことでした。
タップの直後に読むと、前のリストの URL がそのまま返ってきます。
そこで、コピーを叩く前に番兵の文字列をクリップボードへ書き込み、読み出した値がそれと違うものに変わるまでリトライするようにしました。

```python
put_clipboard(SENTINEL)
tap_copy_button()
for _ in range(RETRY):
    value = get_clipboard()
    if value != SENTINEL:
        return value
    time.sleep(WAIT)
```

1 件あたり 20 〜 25 秒、461 件で 2.5 〜 3 時間かかります。
途中で落ちても Firestore に入った分は飛ばして再開できるようにしました。
長時間の走査では、これが無いと検証すらままなりません。

実機ならではの制約もありました。
画面が想定と違う状態になったとき、`am start` で開き直すのが手っ取り早いのですが、連打すると Google マップが ANR で固まります。
画面の再構築は最後の手段に回し、通常は戻るキーで一段ずつ畳むようにしました。

## 収集編 2: 座標は curl では取れない

集まった共有 URL には、座標が入っていません。
リストのピンを地図に置くには緯度経度が要ります。

共有 URL を開くと、まず座標を持たない URL にリダイレクトされます。
そこから SPA がデータを読み終え、`history.replaceState` で `@lat,lng,zoom` が URL に付きます。
つまり座標は、JavaScript が動いた後にしか存在しません。
`curl` で追いかけてもリダイレクト先の URL が取れるだけで、座標は出てきません。

実ブラウザで開き、URL が書き換わるのを待つしかありませんでした。
ここで二つ引っかかりました。

同一タブで続けて別の URL を開くと、地図が再センタリングされないことがあります。
毎回 `about:blank` を挟んでから開くようにして回避しました。

もう一つは、座標が 2 段階で変わることでした。
まず既定のセンター (東京駅付近) が入り、その後に実際の中心へ書き換わります。
早く読むと全件が東京駅になってしまいます。
値が安定するまでポーリングしてから確定させました。

## ピンが全部西にずれていた

こうして 155 エリア分の座標が揃いました。
地図に置いてみると、それらしい位置に並びます。
ただ、どれも街の中心から少し左にいるように見えました。

目視の違和感は、あてになりません。
そこで OpenStreetMap の行政境界と突き合わせ、各エリアの座標がその自治体のポリゴンに入っているかを調べました。

結果は、155 件中 153 件が境界の中心より西寄りでした。
西へのずれの中央値は 3.5 km、最大は大津市の 30 km。
34 件はポリゴンの外に出ていました。

ここで効いたのが、緯度が一致していたことです。
南北には一切ずれず、経度だけが動いています。
地点の取り違えなら南北にも散らばるはずで、そうなっていないということは、原因は場所の側ではなく座標の作られ方の側にあります。

原因は Google マップの左パネルでした。
PC 版の画面は、左に幅 480px のパネルが載り、その下まで地図キャンバスが広がっています。
URL に入る中心座標は、パネルに隠れた部分を含めたキャンバス全体の中心を指します。
利用者が見ている可視領域の中心は、そこから 240px 東にあります。
だから収集した座標は、常にパネルの半分だけ西を指していたわけです。

補正は、そのピクセル差を経度に直せば済みます。
Web メルカトルではタイル 1 枚が 256px なので、ズーム z における 1px は `360 / (256 * 2^z)` 度にあたります。

```python
def correct(lat: str, lng: str, zoom: str, panel: int) -> tuple[float, float]:
    deg_per_px = 360.0 / (256.0 * 2.0 ** float(zoom))
    return float(lat), float(lng) + panel / 2 * deg_per_px
```

ズームが浅いエリアほど 1px の重みが大きくなります。
大津市の 30 km は、広域表示で拾われたために生じていました。

補正後に同じ検証をかけると、境界外は 34 件から 0 件になりました。
経度差の中央値は 3.5 km から 27 m に縮みました。
補正が偶然当たったのではないことは、パネル幅と実測のずれ幅が式の上で一致することから言えます。

パネル幅は実行時にブラウザから取得しています。
Google 側のレイアウトが変われば値も変わるので、定数で埋めるわけにはいきません。

## 設計で捨てたもの

選ばなかった案のほうが、この構成を説明しやすいかもしれません。

**Leaflet + OpenStreetMap**。
地図ライブラリとしては軽く、API キーも要りません。
ただし扱っている対象が Google マップのリストである以上、遷移先と地図の見た目が食い違うのは筋が悪いと考えました。
Maps JavaScript API を選んでいます。

**Cloud SQL**。
600 件弱のデータに常時起動のインスタンス料金を払うのは重すぎます。
Firestore なら実質無料枠に収まります。

**Firebase Hosting から Firestore を直接読み書きする構成**。
報告フォームの検証とレート制限をサーバ側で効かせたかったので却下しました。
セキュリティルールだけで投稿を守るには、書きたい検証が多すぎます。

**静的 TSV のまま配信する**。
読むだけなら足りますが、報告を受け取れません。
TSV は初回インポートと復旧用のシードとしてだけ残しました。

残ったのが Firestore + Cloud Run 1 サービスです。
静的ファイルは `go:embed` でバイナリに入れたので、デプロイ対象はコンテナ 1 個で済んでいます。

## フロントの割り切り

ビルド工程を持たない単一 HTML にしました。
ツリーの開閉は `details` / `summary`、報告フォームは `dialog` で、開閉の JavaScript を書いていません。

CSS フレームワークは Water.css、Simple.css、Pico.css を比較しました。
決め手は `dialog` と `details` の仕上がりで、そこが整っていた Pico.css を採っています。

ツリーの階層は、データモデルを変えずに作りました。
各エリアは所在地とエリア名を持っているので、そのフルパスから都道府県、市、区の階層を機械的に導いています。
階層のためのフィールドを増やすと、収集側と表示側の両方に整合性の責任が増えてしまいます。

都道府県と市区町村の並び順には、総務省の全国地方公共団体コードを使いました。
1,965 行の対応表を 1 ファイルに置き、Go とフロントの両方がそれを読みます。

東京では 191 個のピンが重なりますが、クラスタリングは入れていません。
ズームで足りています。

## 運用

Cloud Build のトリガを 2 本引きました。
PR では検査だけを回し、master への push で検査とデプロイを回します。

検査の中身は Go の `vet` とテスト、Python スクリプトの自己チェック、Node によるツリー構造の検証です。
いずれも Firestore に触らないので、CI 側に本番データへの権限を持たせずに済んでいます。

ドキュメントだけの変更でコンテナを焼き直す必要は無いので、トリガの `ignored-files` で除外しました。

Firestore はスケジュールバックアップを設定してあります。
報告フォームに届いた内容は、コンソールで見てトリアージしています。

## 学び

`curl` で見えないものは実ブラウザに任せます。
SPA が URL を書き換えるタイミングは、外から短絡できません。

「ずれている気がする」はデータで検証します。
OSM の行政境界との突合をやったおかげで、原因の特定と補正の妥当性を同じ物差しで言えました。
緯度が動いていないという観察が、原因を絞る決め手になっています。

Firestore の `(default)` データベースはリネームできません。
後から名前付きデータベースへ移すのは、それなりの移行作業になります。
最初から名前を付けておくほうがよいでしょう。

静的な地名データの持ち場は 1 つにします。
Go とフロントで同じ表を二重に持つと、いずれ片方が古くなります。

Maps の API キーは、公開 URL が確定してから作ります。
先に作ると、リファラ制限をかけられない期間ができてしまいます。
