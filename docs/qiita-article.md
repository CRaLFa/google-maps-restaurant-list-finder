# Google マップの「公式レストランリスト」を地図から探せるようにした話

Google マップには、エリアごとに自動生成される公式のレストランリストがある。
「渋谷: トップリスト」「金沢: 地元で人気」のような、Google が持っている興味と保存のデータから作られる一覧のことだ。
便利なのだが、エリア名を先に知っていないと辿り着けない。
全国にどれだけあるのかを一覧する手段も無い。

そこで、地図のピンから辿れる Web アプリを作った。

<https://google-maps-restaurant-list-finder-bxnbzgrdda-an.a.run.app>

現在 200 エリア / 597 リストを収録している。
開発期間は 12 日、92 コミット、8 PR。
リストの収集に実機の Google マップアプリを自動操作したところ、集めた座標が全件西にずれるという現象に当たった。
この記事では、作ったものの構成と、そのずれの原因を突き止めるまでを書く。

## レストランリストとは何か

**レストランリスト**は、Google マップがエリアごとに用意している公式のおすすめレストラン一覧である。
2024 年 4 月に発表された機能で、ユーザーが作ったリストではなく、そのエリアで人々が興味を持っている店や保存している店のデータから自動で作られる。

エリアごとに 3 種類ある。

- **トップリスト**：常に人気の定番店。長年の実績がある店が並ぶ
- **地元で人気**：まだあまり知られていない近所の名店
- **トレンド**：最近人気が急上昇した店。毎週更新される

アプリでエリア名を検索し、下から出てくるシートを上にスワイプすると表示される。
リストに載っている店の詳細を開けば、その店が入っているリストへのリンクからも辿れる。
いずれの経路でも、エリア名か掲載店のどちらかを先に知っている必要がある。

## 困っていたこと

筆者はこのリストを 460 件ほどフォローしていた。
そうなると、アプリの「保存済み」画面は一覧性が足りない。
フォローした覚えのあるリストを探すのに、延々とスクロールすることになる。

外に持ち出す手段も無かった。
Google Takeout で取れるのは自分が作ったリストだけで、フォローした公式リストの中身は出てこない。
「全国にどんなエリアのリストがあるのか」を知る方法が、どこにも用意されていない。

一覧が手に入らないなら、自分で集めるしかない。

## 作ったもの

- 地図のピンをクリックすると、そのエリアの 3 種類のリストへのリンクが開く
- 地名のインクリメンタル検索でピンとツリーを同時に絞る (「名古屋」と打てば市内の区が出る)
- 都道府県から市、区、エリア、リストへと降りるツリー。並び順は全国地方公共団体コード順
- 漏れているエリアを報告できるフォーム
- ダークモードとスマートフォン表示に対応

## 全体構成

| 層 | 選んだもの |
| --- | --- |
| 収集 | Python + adb + uiautomator で実機の Google マップアプリを操作 |
| 座標取得 | 共有 URL を PC の実ブラウザで開いて読む |
| データ | Firestore (Native モード、名前付きデータベース) |
| サーバ | Go / Cloud Run 1 サービス。静的ファイルは `go:embed` でバイナリ 1 個に同梱 |
| フロント | 単一 HTML + Maps JavaScript API + Pico.css。ビルド無し |
| スパム対策 | reCAPTCHA Enterprise + サーバ側レート制限 |

以下、収集側から順に見ていく。

## 収集編 1: 実機を adb で操作する

リストの一覧は API で取れない。
Web 版の Google マップにも「保存済み」の公式リストは出てこない。
残る経路は、Android 実機のアプリを機械的に操作することだった。

手順はこうなる。

1. 「保存済み」画面を `uiautomator dump` で読み、リスト名を全件収集する
2. 各リストを開いて「共有」から「クリップボードにコピー」を叩く
3. 端末のクリップボードを読み、共有 URL を得る
4. Firestore に upsert する

クリップボードの読み取りには `adb-clip` (端末側で動かす小さなヘルパー) を使った。
`adb shell` からクリップボードを直接読む手段が無いためである。

ここで問題になるのが、コピーが完了したかどうかを知る手段が無いことだった。
タップの直後に読むと、前のリストの URL がそのまま返ってくる。
そこで、コピーを叩く前に番兵の文字列をクリップボードへ書き込み、読み出した値がそれと違うものに変わるまでリトライするようにした。

```python
put_clipboard(SENTINEL)
tap_copy_button()
for _ in range(RETRY):
    value = get_clipboard()
    if value != SENTINEL:
        return value
    time.sleep(WAIT)
```

1 件あたり 20 〜 25 秒、461 件で 2.5 〜 3 時間かかる。
途中で落ちても Firestore に入った分は飛ばして再開できるようにした。
長時間の走査では、これが無いと検証すらままならない。

実機ならではの制約もあった。
画面が想定と違う状態になったとき、`am start` で開き直すのが手っ取り早い。
ところが連打すると Google マップが ANR で固まる。
画面の再構築は最後の手段に回し、通常は戻るキーで一段ずつ畳むようにした。

## 収集編 2: 座標は curl では取れない

集まった共有 URL には、座標が入っていない。
リストのピンを地図に置くには緯度経度が要る。

共有 URL を開くと、まず座標を持たない URL にリダイレクトされる。
そこから SPA がデータを読み終え、`history.replaceState` で `@lat,lng,zoom` が URL に付く。
つまり座標は、JavaScript が動いた後にしか存在しない。
`curl` で追いかけてもリダイレクト先の URL が取れるだけで、座標は出てこない。

実ブラウザで開き、URL が書き換わるのを待つしかなかった。
ここで二つ引っかかった。

同一タブで続けて別の URL を開くと、地図が再センタリングされないことがある。
毎回 `about:blank` を挟んでから開くようにして回避した。

もう一つは、座標が 2 段階で変わることだった。
まず既定のセンター (東京駅付近) が入り、その後に実際の中心へ書き換わる。
早く読むと全件が東京駅になる。
値が安定するまでポーリングしてから確定させた。

## ピンが全部西にずれていた

こうして 155 エリア分の座標が揃った。
地図に置いてみると、それらしい位置に並ぶ。
ただ、どれも街の中心から少し左にいるように見えた。

目視の違和感は、あてにならない。
そこで OpenStreetMap の行政境界と突き合わせ、各エリアの座標がその自治体のポリゴンに入っているかを調べた。

結果は、155 件中 153 件が境界の中心より西寄りだった。
西へのずれの中央値は 3.5 km、最大は大津市の 30 km。
34 件はポリゴンの外に出ていた。

ここで効いたのが、緯度が一致していたことである。
南北には一切ずれず、経度だけが動いている。
地点の取り違えなら南北にも散らばるはずで、そうなっていないということは、原因は場所の側ではなく座標の作られ方の側にある。

原因は Google マップの左パネルだった。
PC 版の画面は、左に幅 480px のパネルが載り、その下まで地図キャンバスが広がっている。
URL に入る中心座標は、パネルに隠れた部分を含めたキャンバス全体の中心を指す。
利用者が見ている可視領域の中心は、そこから 240px 東にある。
だから収集した座標は、常にパネルの半分だけ西を指していた。

補正は、そのピクセル差を経度に直せばよい。
Web メルカトルではタイル 1 枚が 256px なので、ズーム z における 1px は `360 / (256 * 2^z)` 度にあたる。

```python
def correct(lat: str, lng: str, zoom: str, panel: int) -> tuple[float, float]:
    deg_per_px = 360.0 / (256.0 * 2.0 ** float(zoom))
    return float(lat), float(lng) + panel / 2 * deg_per_px
```

ズームが浅いエリアほど 1px の重みが大きい。
大津市の 30 km は、広域表示で拾われたために生じていた。

補正後に同じ検証をかけると、境界外は 34 件から 0 件になった。
経度差の中央値は 3.5 km から 27 m に縮んだ。
補正が偶然当たったのではないことは、パネル幅と実測のずれ幅が式の上で一致することから言える。

パネル幅は実行時にブラウザから取得している。
Google 側のレイアウトが変われば値も変わるので、定数で埋めるわけにはいかない。

## 設計で捨てたもの

選ばなかった案のほうが、この構成を説明しやすい。

**Leaflet + OpenStreetMap**。
地図ライブラリとしては軽く、API キーも要らない。
ただし扱っている対象が Google マップのリストである以上、遷移先と地図の見た目が食い違うのは筋が悪い。
Maps JavaScript API を選んだ。

**Cloud SQL**。
600 件弱のデータに常時起動のインスタンス料金を払うのは重い。
Firestore なら実質無料枠に収まる。

**Firebase Hosting から Firestore を直接読み書きする構成**。
報告フォームの検証とレート制限をサーバ側で効かせたかったので却下した。
セキュリティルールだけで投稿を守るには、書きたい検証が多すぎる。

**静的 TSV のまま配信する**。
読むだけなら足りるが、報告を受け取れない。
TSV は初回インポートと復旧用のシードとしてだけ残した。

残ったのが Firestore + Cloud Run 1 サービスである。
静的ファイルは `go:embed` でバイナリに入れたので、デプロイ対象はコンテナ 1 個で済んでいる。

## フロントの割り切り

ビルド工程を持たない単一 HTML にした。
ツリーの開閉は `details` / `summary`、報告フォームは `dialog` で、開閉の JavaScript を書いていない。

CSS フレームワークは Water.css、Simple.css、Pico.css を比較した。
決め手は `dialog` と `details` の仕上がりで、そこが整っていた Pico.css を採った。

ツリーの階層は、データモデルを変えずに作っている。
各エリアは所在地とエリア名を持っているので、そのフルパスから都道府県、市、区の階層を機械的に導いた。
階層のためのフィールドを増やすと、収集側と表示側の両方に整合性の責任が増える。

都道府県と市区町村の並び順には、総務省の全国地方公共団体コードを使っている。
1,965 行の対応表を 1 ファイルに置き、Go とフロントの両方がそれを読む。

東京では 191 個のピンが重なるが、クラスタリングは入れていない。
ズームで足りている。

## 運用

Cloud Build のトリガを 2 本引いた。
PR では検査だけを回し、master への push で検査とデプロイを回す。

検査の中身は Go の `vet` とテスト、Python スクリプトの自己チェック、Node によるツリー構造の検証である。
いずれも Firestore に触らないので、CI 側に本番データへの権限を持たせずに済んでいる。

ドキュメントだけの変更でコンテナを焼き直す必要は無いので、トリガの `ignored-files` で除外した。

Firestore はスケジュールバックアップを設定してある。
報告フォームに届いた内容は、コンソールで見てトリアージしている。

## 学び

`curl` で見えないものは実ブラウザに任せる。
SPA が URL を書き換えるタイミングは、外から短絡できない。

「ずれている気がする」はデータで検証する。
OSM の行政境界との突合をやったおかげで、原因の特定と補正の妥当性を同じ物差しで言えた。
緯度が動いていないという観察が、原因を絞る決め手になっている。

Firestore の `(default)` データベースはリネームできない。
後から名前付きデータベースへ移すのは、それなりの移行作業になる。
最初から名前を付けておくほうがよい。

静的な地名データの持ち場は 1 つにする。
Go とフロントで同じ表を二重に持つと、いずれ片方が古くなる。

Maps の API キーは、公開 URL が確定してから作る。
先に作ると、リファラ制限をかけられない期間ができてしまう。
